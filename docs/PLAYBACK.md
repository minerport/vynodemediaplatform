# Direct Play and playback sessions

Phase 4 delivers original local media bytes only. The dedicated playback service resolves a typed logical `MOVIE` or `EPISODE` through its physical associations, evaluates every available version against a versioned client capability profile, selects the highest-resolution compatible version (then higher bitrate), and returns either `DIRECT_PLAY` or `UNSUPPORTED` with stable reason codes. A requested version bypasses automatic selection but never compatibility checks. No FFmpeg, remux, HLS, or transcoding fallback exists.

Supported combinations are determined by the submitted profile. The web adapter conservatively reports MP4/H.264/AAC and WebM/VP8-or-VP9/Opus-or-Vorbis only when `canPlayType` reports support. Container, video, every audio stream, resolution limits, and HDR claims participate in the decision. Initial reason codes include `CONTAINER_UNSUPPORTED`, `VIDEO_CODEC_UNSUPPORTED`, `AUDIO_CODEC_UNSUPPORTED`, `RESOLUTION_UNSUPPORTED`, `HDR_UNSUPPORTED`, `MEDIA_UNAVAILABLE`, and `NO_COMPATIBLE_VERSION`.

Playback sessions persist user, login session, logical item, chosen association/file, decision, state, position, duration, timestamps, bytes served, and safe completion/error data. States are `STARTING`, `PLAYING`, `PAUSED`, `STOPPED`, `COMPLETED`, and `ERROR`. A one-hour random media credential is stored only as a SHA-256 digest and returned to the browser as a SameSite, HttpOnly cookie restricted to that session's media path. It is bound to the playback session, user, and still-active login session and authorizes only `GET`/`HEAD`. Raw paths, media credentials, and long-lived login credentials never enter URLs or responses. Native bearer-authenticated requests are additionally checked for matching playback ownership.

Media delivery re-resolves the known file internally, confines it below its recorded source, and compares stored size and nanosecond modification time before opening. It streams with bounded file handles and request cancellation rather than buffering the file. Full requests return `200`; a valid single byte range returns `206`; invalid, unsatisfiable, or multi-range requests return `416`. `Accept-Ranges`, `Content-Length`, `Content-Range`, trusted container MIME, ETag, and Last-Modified are supplied. Concurrent ranges and forward/backward seeking use the same playback session. Multi-range multipart output is deliberately deferred.

The web player uses the native HTML5 video engine and controls. It reports every 12 seconds while active and immediately on pause, seek, completion, and cleanup. Keyboard shortcuts are Space, Left/Right (10-second seek), Up/Down (volume), M (mute), and F (Fullscreen API). Version choice, Auto, resume, Start Over, buffering, unsupported, unavailable, and error states are explicit.

Progress belongs uniquely to user plus logical item, not a physical version. Positions below 30 seconds resume at the beginning. At 90 percent or explicit completion the item becomes watched, its resume position clears, and reopening starts over. Mark Watched/Unwatched is supported. Separate users remain isolated. A multi-episode file is delivered as one shared physical file; independent episode offsets are unknown and no chapter boundaries are fabricated.

Active sessions are abandoned on server startup and after 45 minutes of inactivity; durable progress remains. OWNER/ADMIN can poll the Active Streams API and terminate a session. Normal playback events use `playback_history`, while only administrative termination enters the security audit.

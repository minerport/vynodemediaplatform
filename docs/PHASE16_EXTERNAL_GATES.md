# Phase 16 external release gates

Phase 16 implementation and previously accepted runtime evidence are frozen. Two
external gates remain: production Authenticode/timestamp validation and literal
clean-Windows client/server acceptance. Neither is represented as complete here.

## Production certificate input contract

The tag-only `windows-production-release` GitHub Actions environment consumes:

- `WINDOWS_SIGNING_CERT_BASE64` (secret): Base64 of the production code-signing PFX.
- `WINDOWS_SIGNING_CERT_PASSWORD` (secret): PFX password.
- `WINDOWS_SIGNING_EXPECTED_SUBJECT` (protected environment variable): required
  substring of the Windows-validated signer subject.
- `WINDOWS_SIGNING_EXPECTED_THUMBPRINT` (protected environment variable): exact
  production signing-certificate SHA-1 thumbprint used by Windows certificate APIs.
- `WINDOWS_SIGNING_TIMESTAMP_URL` (protected environment variable): approved RFC
  3161 timestamp endpoint; no credentials are embedded.
- `WINDOWS_UPDATE_PUBLIC_KEY_ID` and `WINDOWS_UPDATE_PUBLIC_KEY_SPKI` (protected
  public variables): update metadata verification identity embedded in the client.
- `WINDOWS_UPDATE_SIGNING_PRIVATE_KEY_BASE64` (secret): Base64 PKCS#8 ECDSA update
  metadata signing key. This is distinct from Authenticode material.

The lane uses Windows SDK `signtool.exe` with SHA-256 file digest (`/fd SHA256`),
SHA-256 timestamp digest (`/td SHA256`), RFC 3161 timestamping (`/tr`), and Windows
Authenticode policy verification (`verify /pa /all /v`). Private material is written
only to a uniquely named temporary PFX and removed in `finally`; it is never an
artifact, log argument, or repository input.

Expected targets are `VyNode.exe`, `vynode-server.exe`,
`VyNode.ServerManager.exe`, Desktop MSI, and Server MSI. FFmpeg/FFprobe are contained
inside the Server MSI, pinned by exact payload hashes and provenance, and are not a
separately published VyNode executable package in Phase 16.

## Fail-closed verification and order

Production input validation occurs before building. Missing PFX/password, expected
identity, timestamp URL, update public identity, or update private key fails the tag
lane. Development/PR artifacts remain unsigned and are labeled `UNSIGNED DEVELOPMENT
BUILD`; `New-ReleaseBundle.ps1 -ReleaseType production` rejects any invalid/unsigned
primary artifact and missing post-signing evidence.

The production order is:

1. Resolve the version from the release tag.
2. Build self-contained Desktop/server/Server Manager payloads.
3. Sign and RFC 3161 timestamp the three first-party executables.
4. Build the MSIs from the signed executable payloads and pinned media tools.
5. Sign and timestamp both final MSI byte streams.
6. Run native Windows trust verification and record signer, thumbprint, SHA-256
   digest, timestamp certificate, validity interval, Windows trust exit status, and
   final file SHA-256.
7. Hash the final signed Desktop MSI and create signed update metadata referencing
   that exact hash.
8. Generate the production release manifest, checksums, SBOM linkage, and notices
   from final signed bytes.
9. Publish only after every earlier step succeeds.

`Test-AuthenticodeRelease.ps1` requires Windows status `Valid`, the configured exact
thumbprint and subject, SHA-256 digest evidence, a timestamp certificate, and a zero
native Windows trust exit code. This is the Windows semantic proof that a trusted
timestamp keeps a signature valid after the leaf signing certificate expires. It
does not predict that result using dates alone. Unsigned, modified-after-signing,
expired-without-valid-timestamp, or untrusted-chain files therefore fail. Actual
production results remain pending until the real certificate is supplied.

## Literal clean-Windows strategy

This host is Windows 11 Home and has no available Windows Sandbox, Hyper-V Manager,
VMware, or VirtualBox clean interactive guest. The current workstation is explicitly
not clean. The lowest-friction valid target is a fresh disposable Windows 11 x64 VM
on separate infrastructure with interactive desktop/UAC support. A fresh physical
machine is also valid. A non-interactive CI runner may verify installation mechanics
but cannot substitute for the login/playback observations.

Generate the ignored transfer directory with:

```powershell
./deploy/windows/clean-machine/New-CleanMachineBundle.ps1 -Production
```

Without `-Production`, the generator creates an explicitly labeled unsigned
preparation bundle for static harness validation only. The real external gate must
use `-Production`, which fails unless both source MSIs are Authenticode-valid.

The bundle contains only two MSIs, hashes/manifest, stock-PowerShell scripts,
instructions, and a short synthetic 640x360 H.264/AAC MP4 generated by the already
approved managed FFmpeg payload. It contains no source checkout, SDK, build tool,
credential, private key, Connect secret, copyrighted media, or development
certificate.

The scripts fail preflight if Visual Studio, .NET SDKs, Go, Node/npm, WiX,
FFmpeg/FFprobe, or Android tools are detected. The installed Desktop is required to
contain `coreclr.dll`, proving the published client is self-contained. Server checks
record any PATH resolution and verify managed binaries under Program Files. Verbose
MSI logs, safe result JSON, service/application logs, and relevant Event Log excerpts
are retained on failure without credentials.

Run `Test-CleanClient.ps1` from a normal user session. It verifies the MSI hash,
installs through UAC, requires observed zero-address login, Home, Search, Movie
Detail, Direct Play/fullscreen, then uninstalls and verifies removal.

After transferring the same bundle, isolate/disconnect the VM network and run:

```powershell
./Test-CleanServer.ps1 -OfflineIsolationConfirmed
```

It verifies no pre-existing media tools, MSI hash, service registration/start,
managed FFmpeg/FFprobe, ProgramData, scoped firewall, readiness, synthetic fixture
scan, representative Direct Play/transcode, Server Manager, uninstall cleanup, and
ProgramData retention. The operator must directly observe authenticated UI/runtime
steps and type `PASS`; the scripts never request or store credentials.

Result JSON records Windows edition/version/architecture, prohibited-tool preflight,
Desktop install/launch/login/Home/search/detail/playback/uninstall, Server
install/service/tools/scan/playback/firewall/manager/uninstall, offline proof,
unexpected dependency findings, and artifact SHA-256 values. A failed or incomplete
field cannot be reported as PASS.
